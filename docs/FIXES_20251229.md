## Fix 1: String Literal Bug (CRITICAL)

### Problem
Extracted service classes had broken string comparisons:
```java
// BROKEN - would never match
if ("parent.y".equals(parent.taxParaYn)) {

// CORRECT - what it should be
if ("Y".equals(parent.taxParaYn)) {
```

### Root Cause
`engines/code_refactor/transformers/transform_engine.py` lines 262-269

The regex for adding `parent.` prefix to field references was matching single-letter field names (y, n, f, e, b, m, x) inside string literals like `"Y"`, `"N"`, `"F"`.

### Fix Applied
```python
# BEFORE (buggy)
for field in all_fields:
    method_body = re.sub(
        rf'(?<![.\w])({re.escape(field)})(?![(\w])',
        r'parent.\1',
        method_body
    )

# AFTER (fixed)
for field in all_fields:
    # Skip very short field names (1-2 chars) as they cause false matches in strings
    if len(field) <= 2:
        continue
    # Prefix field references (not preceded by . or word char or quote, not followed by ( or word char or quote)
    method_body = re.sub(
        rf'(?<![.\w"])({re.escape(field)})(?![(\w"])',
        r'parent.\1',
        method_body
    )
```

### Files Changed
- `engines/code_refactor/transformers/transform_engine.py` (lines 262-285)

## Fix 2: DIVIDE Parser Improvement

### Problem
COBOL `DIVIDE a BY b` statements without GIVING clause were failing:
```
// DIVIDE parse failed: DIVIDE AMOUNT-DIST(IM) BY ERN-CPP-GROSS-SUM
```

### Root Cause
`engines/code_analysis/generators/java_generator_clean.py`

The DIVIDE parser only handled:
- Pattern 1: `DIVIDE a BY b GIVING c`
- Pattern 2: `DIVIDE a INTO b GIVING c`
- Pattern 3: `DIVIDE a INTO b`

Missing Pattern 4: `DIVIDE a BY b` (result stored back to dividend)

### Fix Applied
Added Pattern 4 at line 789-812:
```python
# Pattern 4: DIVIDE a BY b (result back to a) - common in some COBOL dialects
by_match = re.match(
    r'DIVIDE\s+([A-Z0-9-]+(?:\s*\([^)]+\))?)\s+BY\s+([A-Z0-9-]+(?:\s*\([^)]+\))?)',
    content, re.IGNORECASE)
if by_match:
    dividend_cobol = by_match.group(1).strip()
    divisor_cobol = by_match.group(2).strip()

    dividend_java = self.cobol_to_java_name(dividend_cobol)
    divisor_java = self.cobol_to_java_name(divisor_cobol)
    dividend_type = self.get_field_type(dividend_java)

    if dividend_type == 'BigDecimal':
        divisor_wrapped = f'BigDecimal.valueOf({divisor_java})' if divisor_java.replace('.', '').replace('-', '').isdigit() else divisor_java
        expr = f'{dividend_java}.divide({divisor_wrapped}, 10, RoundingMode.HALF_UP)'
        if rounded:
            expr = f'({expr}).setScale(2, RoundingMode.HALF_UP)'
        self.emit(f'{dividend_java} = {expr};', line_num, cobol_ref)
    else:
        self.emit(f'{dividend_java} = {dividend_java} / {divisor_java};', line_num, cobol_ref)
    return
```

### Files Changed
- `engines/code_analysis/generators/java_generator_clean.py` (lines 789-812)

## Fix 3: Auto-Transform for Code Refactor

### Problem
Code Refactor had two separate phases requiring two API calls:
1. `POST /coderefactor` - Analyze only
2. `POST /coderefactor/transform` - Apply recipes

The UI was calling both, but it was confusing and error-prone. Services weren't being extracted consistently.

### Fix Applied

#### 1. Added `auto_transform` parameter to request model
`api/models/code_refactor.py`:
```python
class CodeRefactorRequest(BaseModel):
    scout_account_id: str
    application_name: str
    class_name: Optional[str] = None
    mode: str = "analyze"
    use_ai: bool = True
    recipes_to_apply: Optional[List[str]] = None
    auto_transform: bool = True  # NEW - defaults to True
```

#### 2. Added auto-transform logic to route
`api/routes/code_refactor.py` (lines 156-197):
```python
# Auto-transform: Apply recipes after analyze
transform_results = None
if request.auto_transform and request.mode == "analyze":
    print(f"[Code Refactor] Auto-transform enabled, applying recipes...")
    try:
        from engines.code_refactor.transformers.transform_engine import TransformEngine

        for java_file in java_files:
            class_folder = output_dir / java_file.stem
            recipes_file = class_folder / "artifacts" / "refactor_recipes.json"

            if recipes_file.exists():
                recipes_data = json.loads(recipes_file.read_text())
                recipes_to_apply = recipes_data.get("recipes", [])

                if recipes_to_apply:
                    transform_output = class_folder / "output" / "transformed"
                    transform_output.mkdir(parents=True, exist_ok=True)

                    engine = TransformEngine(str(transform_output))
                    transform_result = engine.apply_recipes(
                        java_file=str(java_file),
                        recipes=recipes_to_apply
                    )

                    transform_results = {
                        "success": transform_result.success,
                        "changes_made": len(transform_result.changes),
                        "files_created": transform_result.files_created,
                        "output_path": str(transform_output),
                    }
                    aggregated_summary["transform_results"] = transform_results

    except Exception as e:
        print(f"[Code Refactor] Auto-transform failed: {e}")
        aggregated_summary["transform_error"] = str(e)
```

### Files Changed
- `api/models/code_refactor.py` (line 17)
- `api/routes/code_refactor.py` (lines 156-197, updated docstring)

## Remaining Known Issues

### Parse Failures (116 occurrences)
These are from multi-line COBOL statements where the parser doesn't accumulate continuation lines. They appear as comments and don't break compilation:
```java
// STRING parse failed (no INTO): STRING "ERROR: " ...
// MULTIPLY parse failed: MULTIPLY HRS-CPP-GROSS-SUM BY...
```

**Impact:** Comments only - code compiles and runs

```java

    // TODO: Implement CALL to external program

```

**Impact:** Need implementation for full functionality


**Impact:** Some control flow may not match original exactly
