### DynamoDB Storage Pattern

**Tenant Isolation via Partition Keys:**
```
TENANT#{tenant_id} / ACCOUNT#{account_id}    → Account data
TENANT#{tenant_id} / JOB#{job_id}            → Job records
TENANT#{tenant_id} / CRED#{profile_name}     → AWS credentials
TENANT#{tenant_id} / FLOW#{flow_id}          → Saved workflows
```

**Example Records:**
- Account: `TENANT#Tims-Test-moderizeit / ACCOUNT#Tims-Test-moderizeit`
- Job: `TENANT#0U812 / JOB#ca_job_1767131434`
- Credential: `TENANT#376129851858 / CRED#default`
- Flow: `TENANT#Tims-Test-moderizeit / FLOW#flow_c2591d2d`

### Key Features
- ✅ Per-tenant data isolation
- ✅ Per-tenant S3 bucket configurations
- ✅ Global Secondary Index for cross-tenant status queries
- ✅ Automatic tenant extraction from job input
- ✅ Backward-compatible API (same function signatures)

### Security Considerations

1. **AWS Credentials in DynamoDB:**
   - Encrypted at rest by DynamoDB
   - Consider migrating to AWS Secrets Manager for production

2. **EC2 Security Group:**
   - Port 8000 is open to 0.0.0.0/0 (internet)
   - OK for development, consider restricting for production

3. **API Authentication:**
   - Currently no auth required
   - Add API keys or OAuth before production

### Multi-Tenant Behavior

**How Tenant ID is Determined:**
1. From request: `scout_account_id` or `account_id` in JSON
2. From environment: `ACCOUNT_ID` env variable
3. Default: `341`

**Each tenant gets:**
- Separate partition key in DynamoDB
- Own S3 bucket configuration
- Isolated job history
- Own saved workflows

